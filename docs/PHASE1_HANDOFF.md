## 3. نتائج المهام والأسباب الجذرية

### Task 01 — إبطال الوصول الفوري

السبب: كان JWT صالحًا كافيًا بعد فحص الحساب، دون التأكد من حالة الجلسة المخزنة. التعديل يقرأ `sid` و`sub` من المطالبات المتحققة، ثم يفحص وجود الجلسة وملكيتها وعدم إبطالها وصلاحية عمرها. تُرفض الجلسة غير الصالحة بـ`401 SESSION_REVOKED`، وتفشل أخطاء التخزين دون منح الوصول. تبقى أولوية أخطاء حالة الحساب وسلوك JWT منتهية الصلاحية محفوظين.

اجتازت حالاتها الـ17 في النسخة المؤقتة مع Task 02 وTask 03، بما فيها logout وlogout-all والاستعادة وإعادة استخدام refresh وفحوص GET وPATCH. هذا التعديل **ليس موجودًا بعد في الفرع الحالي** ولم يُنسخ إليه.

### Task 02 — البريد الإنتاجي

السبب: كان المحول الإنتاجي الوهمي ينتهي دون تسليم فعلي، وتوحي الاستجابة بإتمام الإرسال. أصبحت إعدادات الإنتاج والمصنع والمحول ترفض الحالة غير المدعومة، مع استجابات عامة `accepted` ومنع تسريب أخطاء المزود أو رموز التحقق والاستعادة. الروابط المطبوعة محصورة بمحول التطوير المحلي ومعلّمة DEV-ONLY.

نجحت اختبارات أمان البريد الـ30 واختبارات HTTP للبريد الـ12. **البريد الإنتاجي غير جاهز**: لا يوجد مزود إرسال فعلي، وبدء API في الإنتاج محجوب عمدًا. يلزم تنفيذ مزود معتمد واختباره في بيئة اختبار منفصلة؛ لا يجوز تعطيل الحارس لتجاوز المشكلة.

### Task 03 — ذرّية الاستعادة والحدود

الأسباب: كانت عمليات استهلاك الرمز وتغيير كلمة المرور وإلغاء الجلسات منفصلة، ولا تُبطل كل رموز الاستعادة السابقة. غابت حدود تأكيد الاستعادة والتحقق من البريد، وتجاوزت الاختبارات المحددات. أُثبت أيضًا سباق دخول بكلمة المرور القديمة يتداخل مع الاستعادة.

الإصلاح: معاملة Prisma واحدة بمستوى READ COMMITTED وقفل صف المستخدم، وإعادة قراءة الرمز والتحقق الصارم من انتهائه، واستهلاك مشروط، ثم تحديث كلمة المرور وإبطال الرموز والجلسات وسجل التدقيق. مخزن الذاكرة يستخدم قفل الحساب وتحديثًا متزامنًا بعد تجهيز الحالة. حساب Argon2id خارج المعاملة، مع إعادة التحقق عند الكتابة. إنشاء الجلسة يأخذ القفل نفسه ويفحص نسخة تجزئة كلمة المرور لمنع جلسة جديدة ببيانات قديمة.

الحدود فعالة في الاختبار والتطوير أيضًا. تتضمن الحماية IP ومفاتيح بريد مُطبَّعة ومحمية بـHMAC، وعقد `429 RATE_LIMITED` و`Retry-After`، وفشل تخزين مغلق بـ`503`، وأخطاء استعادة عامة دون معلومات داخلية.

## 7. PostgreSQL: الحالة الفعلية والإجراء المطلوب

لم تتوفر أوامر Docker أو Podman أو psql أو postgres أو pg_ctl أو initdb، ولا خدمات PostgreSQL/Docker مسجلة، ولا تثبيت في مجلدات البرامج المعتادة أو مستمع على 5432/5433. لذلك لم تُنشأ قاعدة، ولم تُطبق ترحيلات محليًا، ولم تُنفذ الحالات الخمس.

الحالات الجاهزة: commit كامل؛ تزامن الرمز نفسه؛ تزامن رمزين للحساب نفسه؛ rollback عند فشل سجل التدقيق مع نجاح إعادة المحاولة؛ رفض إنشاء جلسة ببيانات قديمة بعد الاستعادة.

**النتيجة: ذرّية PostgreSQL والقفل والتراجع والتعافي الفعلي UNVERIFIED / BLOCKED.** اختبارات Prisma الـ11 تستخدم عميلًا محاكى للتحقق من عقد المعاملة ولا تحل محل PostgreSQL.

أصغر خطوة إغلاق: يراجع الإنسان هذا التعديل ويرفعه إلى PR الحالي، ثم يشغل Workflow الجديد على GitHub-hosted runner؛ فهو يجهز الخدمة والقاعدة والترحيل تلقائيًا دون أسرار إنتاج. بديل محلي: تثبيت/تشغيل Docker Desktop بحاويات Linux، ثم تنفيذ الخطوات التالية في نافذة PowerShell منفصلة. هذه تعليمات للإنسان ولم تُنفذ هنا:

```powershell
# From the repository root, with Node 22 / pnpm 10.30.3.
$phase1Password = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(24))
$phase1Container = 'barterzhouse-phase1-' + [Guid]::NewGuid().ToString('N')
$phase1Url = "postgresql://phase1_test:$phase1Password@127.0.0.1:55432/barterzhouse_task03_test"
try {
  docker run --detach --rm --name $phase1Container -p 127.0.0.1:55432:5432 -e POSTGRES_USER=phase1_test -e "POSTGRES_PASSWORD=$phase1Password" -e POSTGRES_DB=barterzhouse_task03_test postgres:16-alpine
  if ($LASTEXITCODE -ne 0) { throw 'Disposable database startup failed' }
  $phase1Ready = $false
  for ($phase1Attempt = 0; $phase1Attempt -lt 30; $phase1Attempt++) {
    docker exec $phase1Container pg_isready -U phase1_test -d barterzhouse_task03_test
    if ($LASTEXITCODE -eq 0) { $phase1Ready = $true; break }
    Start-Sleep -Seconds 1
  }
  if (-not $phase1Ready) { throw 'Disposable database not ready' }
  $env:DATABASE_URL = $phase1Url
  $env:DIRECT_URL = $phase1Url
  $env:TASK03_TEST_DATABASE_URL = $phase1Url
  $env:AUTH_PERSISTENCE = 'memory'
  $env:EMAIL_DELIVERY_MODE = 'memory'
  $env:API_INSTANCE_COUNT = '1'
  pnpm prisma:generate
  if ($LASTEXITCODE -ne 0) { throw 'Client generation failed' }
  pnpm exec prisma migrate deploy --schema prisma/schema.prisma
  if ($LASTEXITCODE -ne 0) { throw 'Disposable migration failed' }
  pnpm --filter @barterzhouse/api test src/modules/auth/stores/password-reset.postgres.test.ts
  if ($LASTEXITCODE -ne 0) { throw 'PostgreSQL integration failed' }
} finally {
  docker stop $phase1Container
  Remove-Item Env:TASK03_TEST_DATABASE_URL -ErrorAction SilentlyContinue
  Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
  Remove-Item Env:DIRECT_URL -ErrorAction SilentlyContinue
  $phase1Password = $null
  $phase1Url = $null
}
```

تُطبق الترحيلات الموجودة فقط على قاعدة جديدة باسم `barterzhouse_task03_test` داخل الحاوية المؤقتة. لا seed ولا reset. لا يُبدّل العنوان بعنوان Neon أو ببيانات اعتماد قائمة. الاختبار نفسه يقبل loopback واسم القاعدة المحدد فقط، ولا يرجع إلى DATABASE_URL. تُوقف الحاوية وتُحذف تلقائيًا بـ`--rm`؛ لا volume دائمًا. تُغلق نافذة الاختبار المنفصلة بعد التنفيذ.

## 8. CI المضاف وحالة التحقق منه

لم يكن هناك مجلد `.github` أو Workflow سابق في الشجرة الحالية. أُضيف Workflow واحد لصلاحية `contents: read`، وأحداث pull_request وpush للفرع الحالي وmain وتشغيل يدوي، مع actions مثبتة إلى SHA وتخزين بيانات Git معطل. لا pull_request_target ولا أسرار أو environment إنتاج، ولا خطوة نشر أو بريد حقيقي.

الترتيب: Node حسب `.nvmrc`، ثم pnpm المثبت، ثم `pnpm install --frozen-lockfile`، وبناء shared، وتوليد Prisma Client، والتحقق من schema، وتطبيق الترحيل الموجود على خدمة PostgreSQL 16 المؤقتة، وTypeScript وESLint، واختبارات PostgreSQL المستهدفة ثم كامل الاختبارات مع تفعيلها، وبناء الإنتاج، وتنسيق الملفات المتغيرة، وفحص whitespace. بيانات الخدمة المنشورة في YAML خاصة بحاوية الاختبار فقط.

فحص التنسيق الجديد يقرأ أسماء الملفات من Git دون shell interpolation، ويشمل الملفات المحلية غير الملتزم بها عند تشغيله محليًا، ويتجاوز الملفات المتجاهلة أو غير المدعومة مثل `.env.example`. يعتمد base على SHA هدف PR أو SHA ما قبل push؛ التشغيل اليدوي يفحص آخر commit. فحص التنسيق الشامل يُبلغ الديون القائمة عبر `continue-on-error`، بينما فحص الملفات المتغيرة إلزامي. يجب جعل فحص الوظيفة كلها مطلوبًا في branch protection.

حالة CI: **منفذ محليًا، محلل YAML وفحص JavaScript وفحص التنسيق ناجحة؛ لم يُشغّل على GitHub**. لم يتوفر actionlint محليًا. تثبيت Linux الجديد وخدمة PostgreSQL وإعداد runner غير متحققة تنفيذيًا بعد، ولا يُدعى نجاحها بناءً على قراءة YAML. ينظف GitHub الخدمة بانتهاء الوظيفة.

مراجع إعداد الخدمة والإجراءات: [دليل PostgreSQL في GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers)، [checkout](https://github.com/actions/checkout)، [setup-node](https://github.com/actions/setup-node). جرى تأكيد SHA المستخدمة بقراءة وسوم المستودعين عبر ls-remote.

## 15. مراجعة الجاهزية الأخيرة قبل commit وpush

**القرار: READY TO COMMIT AND PUSH للملفات الأربعة فقط.** هذا إذن تقني بتقديم التعديل للمراجعة وتشغيل CI، وليس إعلان نجاح GitHub Actions أو موافقة على الدمج أو النشر.

- PR #3 تستهدف `fix/production-email-safety` وفق توضيح المالك. حدث `pull_request` غير مقيد باسم base، ولذلك يشملها. حدث `push` يشمل `fix/password-reset-rate-limiting` صراحةً. أُضيفت أحداث `edited` و`ready_for_review` إلى opened/synchronize/reopened لإعادة التحقق عند تغيير base أو جاهزية PR. توافر زر `workflow_dispatch` يتطلب وصول ملف Workflow إلى الفرع الافتراضي؛ لا يُعتمد عليه لتشغيل هذه الجولة الأولى، بل على push أو PR.
- خدمة PostgreSQL جديدة لكل job على runner مستضاف، بقيم اختبار معلنة فقط، وبلا volumes أو أسرار أو بيانات مشروع. فحص `pg_isready` ينتظر الجاهزية قبل خطوات job، ثم ينشئ الترحيل الموجود schema داخل قاعدة `barterzhouse_task03_test` المحلية فقط؛ نجاح migrate deploy يثبت أيضًا الاتصال ببيانات الاختبار قبل الاختبارات.
- جرى سد فجوة إثبات التنفيذ: `TASK03_REQUIRE_POSTGRES_TESTS=1` يمنع تجاوز مجموعة PostgreSQL بصمت عند غياب عنوانها. تُمرر `TASK03_TEST_DATABASE_URL` في التشغيل المستهدف والتشغيل الكامل. ينتج التشغيل المستهدف تقرير JSON في RUNNER_TEMP، وتفشل بوابة إلزامية ما لم تكن النتيجة خمسة اختبارات ناجحة، وصفر فشل أو skip أو todo، والعدد الكلي خمسة. ينبغي تحديث العدد بقرار مراجعة إذا أُضيفت حالات مستقبلًا.
- نُفذت بوابة التقرير محليًا على تقرير Vitest حقيقي يحوي خمس حالات متخطاة، ورفضته كما يجب. رُفضت أيضًا نتائج اصطناعية ناقصة أو فاشلة أو todo؛ قبول نتيجة اصطناعية من خمسة نجاحات هو اختبار لمنطق البوابة فقط وليس دليلًا على تنفيذ PostgreSQL. نُفذ نمط الإلزام بلا عنوان، وفشل بالرسالة المقصودة قبل الاتصال بقاعدة. حالات الفشل المتعمدة هذه تحقق سلبي ناجح، وليست فشلًا في اختبارات التطبيق.
- أُعيد `pnpm test` بعد التعديل: 163 ناجحًا، صفر فشل، وخمس PostgreSQL متخطاة محليًا. نجح فحص TypeScript مع تضمين ملف اختبار PostgreSQL صراحةً، وESLint للملف، وتحليل YAML وفحص JavaScript المضمن وبوابة التقرير، وفحوص Prettier للملفات الأربعة وللفرق منذ الأب، وdiff --check. نتائج build وبقية فحوص workspace في القسم 11 تخص الجولة السابقة؛ لم يُعد البناء لأن التعديلات الأخيرة محصورة في CI والاختبار والتوثيق.
